The problem

The same invoice, pledged to two lenders. Both pay out.

Lenders can't compare notes

Catching a double pledge means pooling books. A lender's clients and pricing are its business, so nobody shares.

Hash registry: bypassed

FV/2026/09/0412 and FV-2026-09-0412 hash differently. Each bank's spelling is a "new" invoice.

Hash registry: leaks

Anyone holding an invoice hashes it and learns from the public chain whether, and when, it was financed.

OnePledge2

How it works

A canonical ID, a keyed tag, and a proof checked on Midnight.

01 · IDENTITY

KSeF number

Poland's national e-invoicing system assigns every B2B invoice one 35-character number with a CRC-8. One spelling only.

02 · TAG

Keyed, not guessable

The tag authority computes HMAC(key, number) and signs it with the borrower's key and an invoice commitment.

03 · PROOF

Checked in-circuit

The borrower proves the signature, the acceptance window and that the lender is admitted, all in zero knowledge.

04 · LEDGER

Tag set rejects repeats

The tag goes into a public set forever. The second pledge can't produce a valid proof.

Market and roadmap

Start where every invoice already has one ID.

Beachhead: factoring on KSeF

Mandatory national e-invoicing gives every Polish B2B invoice a canonical number. Buyers: factors, supply-chain-finance banks, private-credit funds. Distribution: e-invoicing access points that already connect everyone.

Useful with just two lenders. No consortium needed.

Next

  • Wave 2: Lace-connected borrower desk and lender inbox on Preprod, facilities and borrowing-base draws, encrypted invoice delivery, KSeF test-environment adapter, practitioner interviews
  • Wave 3: threshold tags (no single party can tag), pledge assignment, reusable uniqueness module for any guessable-ID registry
