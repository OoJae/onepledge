The problem

The same invoice, pledged to two lenders. Both pay out.

Lenders can't compare notes

Catching a double pledge means pooling books. A lender's clients and pricing are its business, so nobody shares.

Hash registry: bypassed

FV/2026/09/0412 and FV-2026-09-0412 hash differently. Each bank's spelling is a "new" invoice.

Hash registry: leaks

Anyone holding an invoice hashes it and learns from the public chain whether, and when, it was financed.

How it works

A canonical ID, a keyed tag, and a proof checked on Midnight.

01 · IDENTITY

KSeF number

Poland's e-invoicing system gives each invoice issued through it one 35-character number with a CRC-8. One spelling only.

02 · TAG

Keyed, not guessable

The tag authority computes T = HMAC(key, number). Same invoice, same tag.

03 · ATTEST

One signed digest

Its Jubjub key signs a digest of (domain, registry, T, invoice commitment, day, expiry, borrower key).

04 · PROVE

Tag set rejects repeats

The circuit checks the signature, window, expiry and lender membership, then adds T to a public set forever.

F01: one attestation, 256 pledges

v1 signed only 248 bits of the tag, so changing its last byte passed. v2 signs one SHA-256 digest of the whole attestation, bound to the registry and an expiry. A regression test flips every byte.

Market and roadmap

Start where every invoice already has one ID.

Beachhead: factoring on KSeF

Poland's national e-invoicing gives B2B invoices a canonical number. Buyers: factors, supply-chain-finance banks, private-credit funds. Distribution: the e-invoicing software that already connects them.

Useful with just two lenders. No consortium needed.

Next

  • Wave 2: Lace-connected borrower desk and lender inbox, lender acceptance and void path, encrypted invoice delivery, KSeF test-environment adapter, 2-of-3 upgrade committee, practitioner interviews
  • Wave 3: threshold tags, pledge assignment between lenders, a reusable uniqueness module for any guessable-ID registry
